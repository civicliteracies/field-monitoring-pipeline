# Architecture

What every file in this repository is, and what it does. One entry per file where the code lives,
and one per kind of file in the archive. A change adds an entry for each file it adds, and updates
the entry of any file whose job it changes, so this map grows with the code rather than ahead of it.

## Tools and settings

| File | What it is and does |
|---|---|
| `pyproject.toml` | Names the project, the libraries the code uses and the tools it installs, and holds every tool's settings: the code checker, the type checker, the test runner and the commit message check. |
| `uv.lock` | The exact version of every tool and library, so every machine installs the same ones. |
| `.python-version` | The version of Python this project runs on. |
| `typings/feedparser/__init__.pyi` | Type marks for the one call the code makes to feedparser, which ships none of its own, so the type checker can check the feed route. |
| `typings/pypdfium2/__init__.pyi` | Type marks for the calls the code makes to pypdfium2, which ships none of its own, so the type checker can check the PDF reader. |
| `mise.toml` | The short commands: set the project up, fix what can be fixed while you work, and run the quality gate, which checks linting, formatting, types and tests without changing anything. |
| `.pre-commit-config.yaml` | The checks git runs by itself, at three moments: on commit, the code checker and then the formatter; on the commit message, its shape; on push, the whole quality gate. |
| `.gitignore` | What git leaves alone: caches, the virtual environment, local settings. |
| `config/sources.toml` | The watch list: one table for each source Fieldbook reads, named by its ID, with its name, its address, its route and the topics every one of its items carries, if any. A call source's route is `eu-search`, with the words it searches for, or `eiti-page`. A report source says `kind = "reports"`, and its route is one of four: `report-wordpress`, a WordPress site's address for its posts; `report-feed`, a feed; `report-page`, the links one level below a path on a list page; `report-links`, the links listed. The two dated routes take `since`, the first day an item may be dated. The ID is the name of the source's folder in the archive, and marks its rows in the log. |
| `config/tags.toml` | The topic list: CLI's topics, each marked primary or secondary, the words that also count for some of them, and four lists the topic check reads: the weak words, the names that cancel a match, the words of other sectors and the names not matched as phrases. Before an item is read, it gets every topic its source names on the watch list, and every topic whose name or one of whose words appears as a whole phrase in its head, or as two different phrases that are not weak within ten words of each other in its body. A call's head is its title and call title and its body its description; a report's head is its title and labels and its body its own text; a report found inside a call has its title as its head and the sentences quoted for it as its body. An item with no topic is set aside and gets no card. A card keeps the topics and marks of the day it was made. |

## The runs

| File | What it is and does |
|---|---|
| `.github/workflows/calls.yml` | The daily run. Every morning, or when started by hand from the Actions tab, GitHub runs the one command with the word `calls` and commits what it stored and wrote, the feed included, to the `data` branch. The command gets the model's key from a repository secret. What was written before an error is still committed. A run adds a row to the log for each source it finishes, so a morning with no new call still leaves a commit. `reports.yml` is a copy of it, and each names the other. |
| `.github/workflows/reports.yml` | The weekly run. Every Monday evening, or when started by hand, GitHub runs the one command with the word `reports` and commits what it stored and wrote to the `data` branch. It is a copy of `calls.yml`, with the same steps and the same pinned versions; it differs in its name, its schedule, its job, the command's word and its commit message. |

## The code

The code is in two layers, each in its own folder of the package, with the one command above them.
The data layer, in `data/`, gets each item from its source, a call or a report, keeps a copy, and
checks and sorts each fact into its kind. It holds the shapes of a call and a report, the shapes of
the two lists, the fetch, the store, the shared reading, each kind's reader and the topics. The
presentation layer, in `presentation/`, shows each item: the half of a card for people, and the feed.
The command, `calls.py`, calls them in order. The store, in the data layer, writes and reads back the
record half of every card and writes the cards and the feed, because one module writes every file in
the archive. The tests mirror the same folders.

| File | What it is and does |
|---|---|
| `src/field_monitoring_pipeline/__init__.py` | Marks the folder as the package the run lives in. The file itself is empty. |
| `src/field_monitoring_pipeline/data/__init__.py` | Marks the folder as the data layer's package. The file itself is empty. |
| `src/field_monitoring_pipeline/presentation/__init__.py` | Marks the folder as the presentation layer's package. The file itself is empty. |
| `src/field_monitoring_pipeline/data/fetch.py` | Fetches each source's items by its route. For the EU Funding and Tenders Portal it asks for the grant topics that match each search word, in English, open or announced, reading every page, and keeps each call once as the portal sent it, with its identifier, its link and its title, leaving out those already closed. For EITI it reads the one list of current calls on its consultancy opportunities page and keeps each call once by its full address, with its title and no record; a page that does not hold exactly one such list, holding calls or its empty mark but not both, or a call in it without exactly one title and a link under `/call-for-proposals/`, fails the source, naming what it found. The four report routes keep each report once, by its address: the WordPress route asks every page of the site's posts with their labels, and the feed route reads every entry, both leaving out an item dated before the source's first day and keeping its record, marked by its form; a reply that is not a feed, or an entry with no date or no link, fails the source, and an entry with no title has none until its file gives one. The list page route keeps each link on the same site one level below the source's path, titled by its words where it first appears, or by its file when it has none, and fails the source when it finds none, or when the page holds a link that cannot be read; the single links route asks nothing. One function says whether a date is on or after a given day, for the EU's closed calls and the reports' first day. It also fetches an item's web page or file as the source serves it. |
| `src/field_monitoring_pipeline/data/store.py` | Writes everything under the data folder. Each kind has its own word for a saved item, `saved` for a call and `report saved` for a report, its own card folder, and the kinds whose documents its run reads once more: a reports run reads the calls. For each saved item it writes, in the source's folder, its web page or file as downloaded and, when the source gave one, the source's record of it, both named by a code made from the item's identifier. A call's page ends in `.html`. A report's download ends in the kind of file its first bytes show, `html`, `pdf`, `docx`, `xlsx`, `doc` or `zip`, and its record in the form it came in, `.wordpress.json` or `.feed.json`. For each item read it writes a card into its kind's folder, one for all sources, named by the day the item was saved, its title and the first ten characters of the code of its card key, which is the item's identifier; it gives back a card's day from its name. It writes a card's record half between two `---` lines and reads it back by the card's kind alone, into that kind's record. In one log beside the folders it adds a row for each item the run tried, saved or failed; for each answer the model gave while reading an item, `first answer` or `second answer`, with the answer as it came; and for each item it checked, `set aside`, card written or failed. A call read once more for reports has its answers, then `read for reports` or `failed for reports`, the word and the kind written by one function; a report found in it is named by the call's identifier, `#reports-` and its order, and has its own rows. For each source it adds one more, saying how the run ended for it, and for each card the feed could not read back, a `left out of the feed` row with the card's web address and the reason. It also tells the run which items of a kind are saved, which have a card, which are not yet read (no card and no `set aside` row), which found items already have their row, and a held call's answers the log already keeps, and gives back what was stored for an item: its record, or its page or file when it has none. It lists a kind's cards and writes the feed beside them. |
| `src/field_monitoring_pipeline/calls.py` | The one command. Its first word names the kind, `calls` or `reports`; any other word stops it before any request. It reads the watch list into its typed entries and keeps the sources of that kind, fetches each source's items by its route, skips those already saved, and downloads and stores the rest; an item its source gives no title is titled from its file when it is saved. When an item's page cannot be downloaded, it has the store write that in the log and carries on. When a search fails, or its reply or a link in it cannot be read, it has the store write that as the source's failed run, prints it and goes on to the next source, and the run ends with a failure; any other error while collecting stops the run with nothing written for it. Once a source's items are done, it has the store write how the run ended: `successful`, `failed` or `nothing new`, with the numbers it counted. Then it reads the topic list, which stops the run if it cannot be read or breaks one of its rules, and takes each saved item of the kind that has neither a card nor a `set aside` row. Before any request it checks the item against the topic list, from what was stored for it and the topics its source names; an item with no topic gets a `set aside` row with the check's reason and is never read. It reads each other item with its topics, by its kind's reader, handing the reading a function that has the store write each answer of the model as it arrives, and has the item's card written and a row added with the notes, or a `failed` row with the reason. A calls run then reads each card back on its own and has the feed built from every card it can read back; a card it cannot read back is left out, the store writes its row, and the run ends with a failure. A reports run then reads each call it holds, once, for the reports it names, taking a stopped reading's answers from the log; each report found is checked against the topic list, then gets its card or its `set aside` row, and the call's `read for reports` row comes last. It prints what it did. |
| `src/field_monitoring_pipeline/data/models.py` | The template of a card, for each kind. A call: the fields of a funding call, the ten types a call can have, the call's identifier as the source gives it or else its full address, and the names of the model and the instructions that read it. A report: its title, one of four types, the organisation, who it was for, the method, the results, how long it ran and where, each with its sentence and each of them possibly empty, the day its source gives, empty when it gives none, its link, identifier, model and instructions. An item's topics each carry a name and a mark, primary or secondary, and the template refuses an item with none. It says which fields carry a sentence, or a line written from the source's own field, and which may be empty, and refuses a record that does not fit. Each sentence, and the funder's name, carries a mark saying whether it was found in the stored text. A record cannot be changed once it is made. It also names the two kinds, `calls` and `reports`, the one list of the kinds, for the code and the watch list, and the kinds whose documents a later run reads once more. |
| `src/field_monitoring_pipeline/data/phrases.py` | The one form in which the topic check compares words (case ignored, the hyphen and the non-breaking hyphen read as a space, a run of spacing read as one space) and the shape of a phrase of the topic list. The topic list's shape and the topic check both read it. |
| `src/field_monitoring_pipeline/data/settings.py` | The shapes of the two lists the run reads. The topic list: each topic's mark and the words that also count for it, and the four lists the topic check reads, each required, refusing any other mark, any key it does not know, a weak word that is not a phrase of the list and a name not matched that is not a topic's name, however the list is made; it gives its phrases, each topic's name and words less the names not matched. The watch list: each source's entry by its ID, with its name, address, route, the kind of item its route serves and topics, and what each route takes: the EU route its words, the WordPress and feed routes their first day, the list page route its path and the single links route its addresses. It refuses a missing required field, an unknown one, a route it does not know or a kind its route does not serve; the topics may be left out, and a call source's kind need not be written. |
| `src/field_monitoring_pipeline/data/extract.py` | The calls' reader. It makes the text a language model reads from what was stored for a call. For a call stored with its record: four lines written from the record's fields, then the call's description, when the record has one, and its conditions, with the page's tags stripped. For a call stored as its page alone: the title the list gave, an opening date and a budget not stated, the one date tag on the page, then all the page's visible text, not the contents of its scripts and styles; a page that does not hold exactly one date tag fails its reading before any request. It also gives the topic check what it reads of a stored call: its title, its head (the title with the call title, for a call stored with its record) and its body (that record's description), named as the titles and the description in a set-aside reason; and gives a reports run a held call's text, a page's words without the one-date rule. It takes the topics the check made and prepares the reading: the text, its instructions and how an answer is used. From the four fields, the five facts the model names and those topics it builds the record, marking each quoted sentence, and the funder's name, found or not found in the text; a name not found is never a reason to ask again. Each record comes back with a note for each sentence and name not found, for each empty field among the funder, who can apply and where, saying what the answer did, for an opening date or a budget the source's page has no field for, and for a record with no description. |
| `src/field_monitoring_pipeline/data/reading.py` | The reading every kind shares. It holds the words a reader sees on a page, the quote check, which never finds a quote with no words, the request to the model, the one command line and its flags, pairing a value with its sentence, the notes for an empty fact or a sentence not found, naming the text searched, and the reading of a held document's answer, one item per command line or none for `fieldbook --none`, a line that cannot be read being a problem naming its number while the other lines stand. A kind's reader gives it the text, the name of its instructions, the words that open a second try, its function from a reply to an answer and, for a held document whose reading stopped, the answers the log keeps. It asks, hands each answer on as it arrives, and asks once more in the same conversation when the first answer cannot be used, has a line that cannot be read, or quotes a sentence not in the text; an answer the log already holds stands in place of its request. It keeps the second answer when it can be used, unless the second lost a line and the first lost none, keeps a usable first answer when the second is refused, and fails only when both are refused. |
| `src/field_monitoring_pipeline/data/reports.py` | The reports' reader. It reads a downloaded report by the kind of file its stored name gives: a web page by its words, a PDF page by page, a Word file by its paragraphs and then its table cells, and a spreadsheet by every filled cell, as the values last saved; a file its library cannot read, an old Word or Excel file, a packed file that holds neither part and a PDF with no text, as a scanned one reads, are refused with the reason. It titles an item its source gives no title from its page's or file's own title. It gives the topic check a report's title and labels as its head and its own text as its body, makes the text the model reads, a labelled title line and then that text, and builds the record from the type and the six facts the model names, each sentence marked found or not found, the day the item or entry was posted and the topics the check made, with a note for each sentence not found, each empty fact and a report with no date. For a held call it makes the reading of the reports the call names: one line per report, each giving its title, its type and its six facts, checked by the record's own types; a report found so is checked on its title and the sentences quoted for it, has no date, and its notes speak of the document it was found in. |
| `src/field_monitoring_pipeline/data/tags.py` | The topic list's reader and the topic check. It reads the topic list whole into its shape, so an error names the topic it is in, and refuses a topic a source names that is not on it. Before any request, it decides whether a stored item is in CLI's field, from its title, any other title or label its source gives it, its body, and the topics its source names. A phrase matches as a whole phrase, with both sides read in the one form. A cancelling name is taken out first, wherever it appears. Every phrase in the head gives its topic, unless the title holds no phrase outside a cancelling name and names another sector; in the body, two different phrases that are not weak, different in form, at different places and neither inside a longer phrase found there, give their topics when they stand within ten words of each other. An item with a topic, or whose source names topics, is kept with its topics in the list's order, each once; any other is set aside with the reason: what its head gave, and that its body held no two such phrases near each other, each named by the item's own parts. |
| `src/field_monitoring_pipeline/data/instructions/v3.md` | The instructions the model reads for a call, in plain words: what the text is, the three passes, the fields and their sentences, and the one command line to write. The record notes their name. |
| `src/field_monitoring_pipeline/data/instructions/reports-v1.md` | The instructions the model reads for a report: what the text is, the three passes, the type and the six facts with their sentences, the line that keeps personal details out of a quote, and the one command line to write. ## The archive, on the `data` branch

The `data` branch holds the archive and shares no history with the code. The log appears with the
first run, an item's page or file and any record of it once that item is saved, its card once it is read, and the
feed once a calls run reaches its end.

| File | What it is and does |
|---|---|
| `.gitattributes` | Tells git to convert no line endings on this branch, so a stored page is the same bytes on every machine. |
| `README.md` | The branch's front page: what the branch is for. |
| `data/raw/log.csv` | The log: one row for each item a run tried, saved or failed, one for each answer the model gave while reading an item, with the answer as it came, one for each item it checked, set aside, card written or failed, the rows of a call read once more for reports, each naming the kind, and one for each source, saying how the run ended for it, and one for each card the feed could not read back, with the card's web address and the reason. |
| `data/raw/<source ID>/<code>.html` | A saved call's web page, exactly as downloaded. |
| `data/raw/<source ID>/<code>.json` | The source's record of the same call, every value as sent, where the source gives one: an EU call has one, an EITI call has none. |
| `data/raw/<source ID>/<code>.<file type>` | A saved report's download, exactly as it arrived, ending in the kind of file its first bytes show: `html`, `pdf`, `docx`, `xlsx`, `doc` or `zip`. |
| `data/raw/<source ID>/<code>.<form>.json` | The record a WordPress site or a feed gave of the same report, every value as sent, ending in its form, `wordpress` or `feed`. |
| `data/calls/<day saved>-<short title>-<short code>.md` | A call's card, written once when the call is read and never rewritten. Its name ends in the first ten characters of the call's code. |
| `data/reports/<day saved>-<short title>-<short code>.md` | A report's card, written once when the report is read and never rewritten. A report found inside a call is named by the day of that reading. |
| `data/feed.xml` | The RSS feed, rebuilt on each run, one entry for each card it can read back. A feed reader fetches it from its raw address on this branch. |
