# Architecture

What every file in this repository is, and what it does. One entry per file where the code lives,
and one per kind of file in the archive. A change adds an entry for each file it adds, and updates
the entry of any file whose job it changes, so this map grows with the code rather than ahead of it.

## The front of the repository

| File | What it is and does |
|---|---|
| `README.md` | The front page: what Fieldbook is, what it does, how a run works, what the checks do not prove, and what this version covers. |
| `CONTRIBUTING.md` | How to set the project up and what the automatic checks do. |

## The records

| File | What it is and does |
|---|---|
| `docs/plan.md` | What is being built, in order, ticked by the change that completes each line. |
| `docs/decision-log.md` | How Fieldbook handles what it collects, by topic: the pending decisions first, then the goal, the shape of a run, and every decision the code cannot show. |
| `docs/bug-history.md` | Serious faults: the open ones first, then each fault that was fixed, with its cause, its fix and the rule it produced. |

## Tools and settings

| File | What it is and does |
|---|---|
| `pyproject.toml` | Names the project, the libraries the code uses and the tools it installs, and holds every tool's settings: the code checker, the type checker, the test runner and the commit message check. |
| `uv.lock` | The exact version of every tool and library, so every machine installs the same ones. |
| `.python-version` | The version of Python this project runs on. |
| `mise.toml` | The short commands: set the project up, fix what can be fixed while you work, and run the quality gate, which checks linting, formatting, types and tests without changing anything. |
| `.pre-commit-config.yaml` | The checks git runs by itself, at three moments: on commit, the code checker and then the formatter; on the commit message, its shape; on push, the whole quality gate. |
| `.gitignore` | What git leaves alone: caches, the virtual environment, local settings. |
| `config/sources.toml` | The watch list: one table for each source Fieldbook reads, named by its ID, with its name, its address, its route (`eu-search` or `eiti-page`), the topics every one of its calls carries, if any, and for the EU portal the words it searches for. The ID is the name of the source's folder in the archive, and marks its rows in the log of calls. |
| `config/tags.toml` | The topic list: CLI's topics, each marked primary or secondary, and for three of them a few words that also count. A call gets every topic its source names on the watch list, and every topic whose name or one of whose words appears as a whole phrase in a label its source put on it. A card keeps the topics and marks of the day it was made. |

## The daily run

| File | What it is and does |
|---|---|
| `.github/workflows/calls.yml` | The daily run. Every morning, or when started by hand from the Actions tab, GitHub runs the one command and commits what it stored and wrote, the feed included, to the `data` branch. The command gets the model's key from a repository secret. What was written before an error is still committed. A run adds a row to the log for each source it finishes, so a morning with no new call still leaves a commit. |

## The code

| File | What it is and does |
|---|---|
| `src/field_monitoring_pipeline/__init__.py` | Marks the folder as the package the run lives in. The file itself is empty. |
| `src/field_monitoring_pipeline/fetch.py` | Fetches each source's calls by its route. For the EU Funding and Tenders Portal it asks for the grant topics that match each search word, in English, open or announced, reading every page, and keeps each call once as the portal sent it, with its identifier, its link and its title, leaving out those already closed. For EITI it reads the one list of current calls on its consultancy opportunities page and keeps each call once by its full address, with its title and no record; a page that does not hold exactly one such list, holding calls or its empty mark but not both, or a call in it without exactly one title and a link under `/offers/`, fails the source, naming what it found. It also fetches a call's web page as the source serves it. |
| `src/field_monitoring_pipeline/store.py` | Writes everything under the data folder. For each saved call it writes the call's web page as downloaded in the source's folder and, when the source gave one, the source's record of it. Both are named by a code made from the call's identifier. For each call read it writes a card into one folder for all sources, named by the day the call was saved, its title and the first ten characters of its code. In one log beside the folders it adds a row for each call the run tried, saved or failed; for each answer the model gave while reading a call, `first answer` or `second answer`, with the answer as it came; and for each call it read, card written or failed. For each source it adds one more, saying how the run ended for it. It also tells the run which calls are saved, which have a card, and gives back what was stored for a call: its record, or its page when it has none. It lists the cards and writes the feed beside them. |
| `src/field_monitoring_pipeline/calls.py` | The one command. It reads the watch list into its typed entries, fetches each source's calls by its route, skips those already saved, and downloads and stores the rest. When a call's page cannot be downloaded, it has the store write that in the log and carries on. When a search fails or its reply cannot be read, it has the store write that as the source's failed run, prints it and goes on to the next source, and the run ends with a failure; any other error while collecting stops the run with nothing written for it. Once a source's calls are done, it has the store write how the run ended: `successful`, `failed` or `nothing new`, with the numbers it counted. Then it reads the topic list, which stops the run if it cannot be read or lacks a topic a source names, and reads each saved call that has no card from what was stored for it, with that list and the topics its source names, handing the reading a function that has the store write each answer of the model as it arrives, and has the call's card written and a row added with the notes, or a `failed` row with the reason. Last, it has the feed built from every card. It prints what it did. |
| `src/field_monitoring_pipeline/models.py` | The template of a card: the fields of a funding call, the ten types a call can have, the call's identifier as the source gives it or else its full address, and the names of the model and the instructions that read it. A call's topics each carry a name and a mark, primary or secondary, and a call may have none. It says which fields carry a sentence, or a line written from the source's own field, and which may be empty, and refuses a record that does not fit. Each sentence carries a mark saying whether it was found in the stored text. A record cannot be changed once it is made. It also holds the shape of the topic list: each topic's mark and the words that also count for it, refusing any other mark and any key it does not know. And it holds the shape of the watch list: each source's entry by its ID, with its name, address, route and topics, and the words the EU route takes, refusing a missing required field, an unknown one or a route it does not know; the topics may be left out. |
| `src/field_monitoring_pipeline/extract.py` | The reading. It makes the text a language model reads from what was stored for a call. For a call stored with its record: four lines written from the record's fields, then the call's description, when the record has one, and its conditions, with the page's tags stripped. For a call stored as its page alone: the title the list gave, an opening date and a budget not stated, the one date tag on the page, then all the page's visible text, not the contents of its scripts and styles; a page that does not hold exactly one date tag fails its reading before any request. Before any request, it gives the call the topics its source names and those of the topic list that the labels its source put on it name. It asks the model, hands each answer on as it arrives, and reads the one command line of the answer. From the four fields, the five facts the model names and those topics it builds the record, marking each quoted sentence found or not found in the text. When the answer cannot be used or a sentence is not found, it asks once more in the same conversation, with a message naming each problem. Each record comes back with a note for each problem and each sentence not found, for each empty field among the funder, who can apply and where, saying what the answer did, for an opening date or a budget the source's page has no field for, for a record with no description, and for a call with no topic. |
| `src/field_monitoring_pipeline/tags.py` | The topic list's reader and matcher. It reads the topic list whole into its shape, so an error names the topic it is in, and refuses a topic a source names that is not on it. It gives a call the topics, each with its mark, that its source names, or whose name or one of whose words appears as a whole phrase in one of the labels its source put on it. Both sides are read in one form: case ignored, a hyphen read as a space, and a run of spacing read as one space. The topics come in the list's order, each once. |
| `src/field_monitoring_pipeline/instructions/v3.md` | The instructions the model reads, in plain words: what the text is, the three passes, the fields and their sentences, and the one command line to write. The record notes their name. |
| `src/field_monitoring_pipeline/write.py` | The card. It writes a record as one Markdown file. The record sits on top, in a block GitHub shows as a table. Below it come the facts for people, each with its sentence or line, a warning under a sentence not found, then the link and the model that read it. The same module reads the block back into the same record. |
| `src/field_monitoring_pipeline/publish.py` | The feed. It writes RSS from the cards, one entry per card in the order of their names. Each entry holds the title with the closing date, a link to the card on github.com, the summary, one category for each of its topics and one for each mark they carry, primary before secondary, told apart by their RSS `domain`, and the call's code as its identity. No date of the build goes in, so the same cards give the same file. |
| `tests/__init__.py` | Marks the tests folder as part of the project. |
| `tests/test_placeholder.py` | One passing test, from the project's first setup. |
| `tests/test_fetch.py` | Checks the fetch against recorded portal replies and hand-made EITI pages, so no test needs the internet: the real watch list read into its typed entries with its topics on the real topic list, the fetch taking the reader of each source's route, EITI's reader returning each current call once by its full address with its title, its empty list giving no calls, a page that is not its list or not UTF-8 refused naming what it found, EITI's list refusing a request, a card with no title or two, a list holding calls and its empty mark, a line break inside a heading, one call per identifier, each call's title and whole record, closed calls left out, every page read, what the request asks for, a web page kept whole, the client's own settings, and a redirect that stops the fetch. |
| `tests/test_store.py` | Checks the store in a temporary folder: the code that names a call's files, the page kept byte for byte, the record written with every value as sent, the files written before the log row, a record that cannot be written, which calls count as saved and on which day, the log's rows and its first line, a failed call's row, the run's row in each of its three words, a card's name and its short title, cut at the last hyphen within its first 61 characters, on a long title, a curly apostrophe and a title of exactly 60 characters, with and without a word after it, a card written and found for its own call only, a stored record read back, a call with no record stored as its page alone and read back as it, the reading's row, an answer's row holding its word and the answer read back whole, line breaks, a lone carriage return and quotation marks included, the listing of the cards, and the feed written as UTF-8 with line feeds. |
| `tests/conftest.py` | The test watch list and the test topic list, written into each test's folder, for each of the command's test files. |
| `tests/test_calls.py` | Checks the command's collecting against recorded portal replies, so no test needs the internet: a first run that saves every call, a second that adds only the run's row and reads none, closed calls left out by the run's clock, a call whose page fails and is tried again, then saved and read that morning, a page that cannot be downloaded and is logged on every run, a link that cannot be read, every failed call counted, any other error on a page stopping the run with no row written for it, two sources kept apart, each with its own row for the run holding its own word and numbers, a watch list with a field missing refused before any request, the command ending with a failure when a call has failed, and the file run as the command. | `tests/test_calls_sources.py` | Checks the command across its sources, with the recorded portal and EITI's stand-in site: a search that fails, a search reply that is not JSON and a reply the fetch cannot read, each the source's failed run while the run carries on; after a failed search, the next source searched and the saved calls read; a second source whose reply lacks a field stopping the run after the first source's row; an EITI link that cannot be read failing only its call; a page in place of EITI's list being EITI's failed run; and a topic a source names that is not on the topic list stopping the run after the calls are stored, and EITI's list refusing the request being EITI's failed run. |
| `tests/test_calls_reading.py` | Checks the command's reading and its feed, with the recorded portal and a stand-in model: each saved call without a card read once, by source and then identifier, a call whose source has left the watch list carrying only its labels' topics, a record with no description read from its conditions, with its note, each answer the model gave written in the log as it came, before the call's card and its row, the notes reaching the log, two of them in one row, a reading that fails, because the model service refuses it or both its answers cannot be used, written as failed after its answers, counted and read again the next run, its card still named by the day the call was saved, a morning with no key saving every call and failing every reading, a card that cannot be written stopping the run after the call's answer and before its card, a reply with no content leaving its empty answer row before the run stops, any other error in a reading stopping the run with what was written before it kept and no feed written, a call whose labels match no topic noted in its card's row, a topic list that cannot be read stopping the run after the calls are stored, with no card and no feed written, and stopping a quiet morning too, with the feed left as it was, an EITI call saved as its page alone and read from it, its opening date and budget noted as having no field and its source's topic on its card and in the feed, and the feed built from every card after the reading, each entry carrying its card's topics and marks, built again when its file is missing, and holding the cards of a morning on which one reading fails. |

## The archive, on the `data` branch

The `data` branch holds the archive and shares no history with the code. The log appears with the
first run, a call's page and any record of it once that call is saved, its card once it is read, and the feed once a
run reaches its end.

| File | What it is and does |
|---|---|
| `.gitattributes` | Tells git to convert no line endings on this branch, so a stored page is the same bytes on every machine. |
| `README.md` | The branch's front page: what the branch is for. |
| `data/raw/log.csv` | The log of calls: one row for each call a run tried, saved or failed, one for each answer the model gave while reading a call, with the answer as it came, one for each call it read, card written or failed, and one for each source, saying how the run ended for it. |
| `data/raw/<source ID>/<code>.html` | A saved call's web page, exactly as downloaded. |
| `data/raw/<source ID>/<code>.json` | The source's record of the same call, every value as sent, where the source gives one: an EU call has one, an EITI call has none. |
| `data/calls/<day saved>-<short title>-<short code>.md` | A call's card, written once when the call is read and never rewritten. Its name ends in the first ten characters of the call's code. |
| `data/feed.xml` | The RSS feed, rebuilt from every card on each run, one entry per card. A feed reader fetches it from its raw address on this branch. |
