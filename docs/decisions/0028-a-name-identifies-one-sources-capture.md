# ADR-0028 — A name identifies one source's capture; matching one call across sources moves to the card [decision]
**Status:** Accepted (2026-09-02). **Owner:** CLI. Supersedes in part [ADR-0026](0026-item-names-are-always-hashed.md), which set the three naming rules and their order. The rules and their order are unchanged; what each one hashes now includes the source.
**Context.** An item's name is its filename. Three rules produce one, in order of preference: the source's own identifier for the item, else the canonical link, else the body. Only the first carried the source. Two sources that both carried a funding call, an aggregator and the funder itself, would therefore produce one name under the second rule, and the second capture would overwrite the first: its body, and the record of where it came from, gone, with the run log reporting two new items where the archive held one. The exposure was worse than a plain gap because **which rule applies depends on what a publisher includes.** Nine feeds in this sector were fetched to check: every one of the five that answered publishes a per-item identifier, and both live captures use the first rule. So the collision fires only for a publisher who omits one, and the same two sources would collide or not depending on which software a funder happens to run. The original plan states three times that the same call arriving from several places is stored once and surfaces once, and names storing it several times as one of the fastest ways to lose trust, so collapsing the two captures into one was examined first and at length. It was rejected on evidence. A source that republishes a call links to its own page rather than to the original: on the two republishing feeds that answered, every one of ten item links pointed at the publisher's own site. Canonicalisation works on the text of a link and resolves no redirect, which this project deferred deliberately, so two sources do not produce one address for one call and a name built from the link cannot match across them. A collapse would also have kept one body per name, so the archive that every card is rebuilt from would have changed depending on which source ran last.
**Decision.** Every naming rule carries the source. A name therefore identifies one source's capture, never a call in the world, and no run can write over what another source captured. The canonical link is still recorded in every origin record, un-namespaced and whole, because it is the evidence a later step uses; only the name is namespaced. Recognising that two captures are the same call moves to the card, where the funder, the title and the deadline are the evidence rather than two strings being equal, and it is scheduled with the slice that adds the second call source rather than left open. Canonicalisation keeps its place: one source listing the same call twice with different tracking parameters still collapses to one capture, because the source is the same on both.
**Consequences.** Nothing a run writes can overwrite another source's capture, whatever a publisher publishes, and the behaviour no longer varies with a publisher's habits. The archive becomes stable input, which is what the rebuild step needs to give the same cards from the same files on any day. The run log stops being able to overstate what is on disk: two captures are two captures. Three things are given up knowingly. The plan's "captured once" is not delivered, and cannot honestly be at capture time; what is delivered is captured once per source and surfaces once, and the second half is where it matters, because the feed and the dashboard are what CLI sees and the archive is not. Two sources carrying one call cost two small text files, which the free tier does not notice. And cross-source matching is now work owed at a later slice rather than a property of the store; the open-source feed readers have not solved it either, so it deserves the care rather than an assumption. Migration is nothing, because this lands before any capture has been published: the archive branch holds a note and no items. That is true today and false after the first scheduled run, which is why it lands now.
