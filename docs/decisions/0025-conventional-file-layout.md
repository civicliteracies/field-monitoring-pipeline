# ADR-0025 — The conventional layout for decision records and specifications [decision]
**Status:** Accepted (2026-09-01). **Owner:** CLI. Supersedes in part [ADR-0003](0003-adopt-numbered-adrs-for-the-decision-log.md) and [ADR-0017](0017-bug-history-is-a-separate-file.md), in both cases only where they name a file that has since moved. What each of them settled still holds.
**Context.** A review against published conventions found three places where this repository had invented a name for something that already has a standard one, and a fourth that looked like one and is not. Decision records are conventionally one file per record under `docs/decisions/`, numbered, titled with dashes, with an index beside them; here they were twenty-four records in a single file, which meant every new record arrived as a diff against a long document and the file was already at the length where people stop opening it. Specifications conventionally sit in `specs/`, which is the layout used by the spec-driven tooling this project's Constitution pattern comes from; here the folder was called `issues/`, which is also GitHub's own name for its bug and task tracker, so the name pointed a reader at the wrong thing. And a changelog is conventionally opened before the first release rather than reconstructed after it. Each of those three departures carries the same cost, which is that someone who already knows the convention has to learn this project's version instead. None had been published, so the change costs one edit and breaks no link that exists anywhere. The fourth candidate is `docs/BUGS.md`, and it was examined on the same test and kept. A file recording defects has no convention behind it either: the usual arrangement is the tracker while a defect is open, a changelog line once it is fixed, and the commit for the detail. But recording every problem and how it was fixed, so the same one is not rediscovered and a maintainer can see how the system behaves under stress, is a stated requirement of this project rather than a guard against a hypothetical risk, and the scattered arrangement does not deliver it: a reader would have to open closed issues one at a time, and a changelog line says what changed for someone using Fieldbook rather than what broke or why. This is the same distinction that kept `docs/ARCHITECTURE.md` in [ADR-0022](0022-the-gate-is-the-four-standard-checks.md).
**Decision.** Adopt the conventional layout. The records move to `docs/decisions/NNNN-title-with-dashes.md`, one file each, with `docs/decisions/README.md` as the index; the text of every record moves unchanged, and only the Status field of a superseded record is touched, which is the field that exists to change. `issues/` becomes `specs/`, and the specification is numbered rather than dated, because git already carries the date. `CHANGELOG.md` is added at the root in the Keep a Changelog format, opening with an Unreleased section. `docs/BUGS.md` keeps its place and its format: one entry per defect carrying its symptom, its cause, its fix, and the test that now guards it, newest first. A defect sits in the repository's issue tracker while it is open, moves to the history once it is fixed, gets a line under Fixed in the changelog when someone using Fieldbook would notice the difference, and earns a numbered record here when its fix sets a lasting rule, with the incident and the rule linking to each other rather than repeating each other. The two entries it already held stay, and the rules they established remain recorded as [ADR-0001](0001-deadline-validates-as-a-valid-date.md) and [ADR-0002](0002-heartbeat-proves-liveness-not-emptiness.md). The rule that a fix must add a test failing on the pre-change behaviour is written into `CONTRIBUTING.md` as well as `AGENTS.md`. `constitution.md` keeps its name and its place at the root, with one line naming the pattern it follows so that it reads as a known thing rather than an invention.
**Consequences.** Every folder name here is now one an experienced developer has seen before, which is the whole point: the repository stops asking to be learned. Adding a record becomes a commit that creates one file and touches nothing else, so the reasoning reviews cleanly on its own. Two things are given up. The reasoning can no longer be read top to bottom in one scroll, which the index covers in part but not wholly. And record filenames become effectively permanent, because renaming one breaks every link to it, which suits the immutability rule this log already follows. Keeping `docs/BUGS.md` carries a cost of its own, and it is the same one `docs/ARCHITECTURE.md` carries: it is not a file an experienced developer expects to find, so it is one more thing to learn about this repository, and nothing enforces it, so it stays current by judgement and a review pass before pushing rather than by a check. The threshold rule, the format of a record, and the rule that accepted records are never rewritten are all unchanged.
