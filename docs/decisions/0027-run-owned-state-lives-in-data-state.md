# ADR-0027 — Run-owned state lives in `data/state/`, apart from configuration [decision]
**Status:** Accepted (2026-09-01). **Owner:** CLI.
**Context.** Reaching a source with a conditional request means sending back the value the source gave last time, so an unchanged source can answer in one short exchange rather than sending its whole body again. That value has to be kept somewhere between runs. The original plan requires conditional requests but never says where the value lives, and the documented layout of `data/` has places only for the raw archive, the cards, the reports and the quarterly notes. Two obvious homes were considered and rejected. Keeping it in `config/sources.toml` would mean the run writes to a file people edit by hand, which is the one collision the split between configuration and data exists to prevent. Deriving it from the timestamps already in the archive would avoid a new folder but supports only a date-based question, which is weaker than the identifier most sources offer, and would mean reading many files at the start of every run.
**Decision.** A `data/state/` folder holds one small file per source, carrying whatever that source gave to identify its current version. It sits inside `data/`, which the run owns, and never inside `config/`, which people own. The rule is stated plainly: **people write `config/`, the run writes `data/`, and neither writes the other's.** Every write in the run goes through one function rooted at `data/`, so addressing `config/` cannot be expressed.
**Consequences.** A hand edit to the watch list and a scheduled run can never conflict, because they touch different directories, and that is now a property of the code rather than a convention to remember. An unchanged source costs almost nothing to check, which matters on a free tier and to the sources being polled. Two things are given up. The documented layout gains a folder that neither plan shows, which is one more thing for a maintainer to learn, mitigated by its being named for what it holds. And the stored value is a cache: deleting it costs one full fetch per source, and the run after the deletion labels that source a first look again, which changes one line of the run log and nothing else. The folder never needs backing up or repairing. Not every server honours a conditional request, so this is a cost saving rather than a correctness mechanism; the item-name gate is what actually prevents a second capture.
