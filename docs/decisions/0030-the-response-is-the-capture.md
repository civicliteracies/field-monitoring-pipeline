# ADR-0030 — The response is the capture; items are derived from it, never instead of it [decision]
**Status:** Accepted (2026-09-02). **Owner:** CLI.
**Context.** The rule the whole design rests on is capture before derive: what a source served is written down before anything reads it, so everything else can be rebuilt from it. The code did not do that. It fetched a response, parsed it, dropped every item published before the source's cutoff, reduced each survivor to its title, summary and content joined together, wrote those, and discarded the bytes the source had served. Probing it showed what that costs: a feed carrying a publication date, an author and a category archived none of the three, and the original response was nowhere, not on disk and not in git, because it had never been written. So the archive was not what the source served but what one version of one function made of it, and anything that version did not look at was gone for good. That is a quiet failure rather than a loud one, which is why it survived a specification, a review and fifty three passing tests: everything downstream worked, on less than it should have had.
**Decision.** The fetch step returns the response unread. The run writes it down, and only then reads items out of it. Responses live in `data/responses/<source_id>/`, named by a hash of their own bytes, so a source that serves the same response tomorrow writes the same file and the archive does not churn, while a source that changes leaves both versions behind. Every item's record names the response it was read out of, so anything derived later can be traced to the exact bytes it came from. Reading a response into items is now a separate function that runs after the capture, never inside the fetch.
**Consequences.** The archive becomes what its name claims: everything the source said, not the part this version of the code happened to want. A later slice that needs a publication date, an author, a category or a namespaced element can have it without re-fetching, which for a closed call is not possible at all. The rebuild step gains a stable input, so the same archive gives the same cards on any day. It also settles a defect that was open separately: an item edited at the source still overwrites its own body, but the response it first came in is kept, so the original wording is recoverable rather than lost. Three costs, all accepted. The archive grows by a response per source per change rather than per item, which for a feed is tens of kilobytes and which the original plan already anticipates by asking for a retention policy in maintenance. Where a source changes daily, so does its stored response, so the archive commits on those days, which is honest rather than noisy because the source did change. And a run now writes a response even for a source it then cannot read, which is deliberate: a holding page is the evidence that a source is blocked, and throwing it away would leave nothing to look at.
