# ADR-0029 — The archive records facts about the item, never about the run [decision]
**Status:** Accepted (2026-09-02). **Owner:** CLI. Refines the origin record's contents, which the original plan gives as the source, the link, the time of fetching and the hash.
**Context.** Each captured item is a body and a small record beside it. The record stored the moment the item was fetched, taken fresh on every run. Bodies never churned, because writing identical bytes is not a change, but records did, on that timestamp alone. Rehearsing a whole scheduled run twice showed the consequence: a day on which nothing at the source had changed still produced a commit, and the branch that exists in the workflow to say "nothing new to commit" could never run. Over a year of quiet that is several hundred commits recording nothing, and the archive's history stops answering the question it exists to answer, which is when an item actually changed. Every test passed throughout, and a single live run looked perfect, because the fault only appears on the second day.
**Decision.** Every field in the origin record is a fact about the item rather than about the run that happened to see it, so capturing the same item again writes the same bytes. The time recorded is when the item first entered the archive, and it does not move afterwards, not even when the item's words later change: the item is the same item. When the run last looked is the run's own business and already has a home in the bookmark kept per source, which does not churn because a source that has not changed returns the same value or answers that nothing has changed at all.
**Consequences.** A quiet day leaves the archive untouched, so an entry in its history means an item genuinely changed and the history is worth reading. The workflow's own guard against an empty commit can now do its job. Two things follow that are worth stating. Reading the record back before writing it is what makes this work, and that read is the only one in the archiving step; it treats a record it cannot parse as absent, so a file half written by a machine that was torn down cannot stop the next run. And "when did we last see this item" is no longer answerable from the archive alone; nothing needs it today, and if something does, git already records when each file last changed. The general rule this sets, and the reason it is written down rather than left as a fix: **a value that changes every run does not belong in a store whose history is meant to mean something.** That test applies to anything added to a record here later.
