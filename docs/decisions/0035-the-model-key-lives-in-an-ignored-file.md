# ADR-0035 — The model key lives in an ignored file beside the code, not in an account-wide variable [decision]
**Status:** Accepted (2026-09-03). **Owner:** CLI.
**Context.** The extraction step needs a key. On the scheduled run that is a repository secret, which is settled and is not this decision. On a maintainer's machine there were four real options: a file the project reads and git ignores, the same file loaded into every task by the task runner, an account-wide environment variable, or the operating system's credential store reached through a library. The credential in question is a free-tier key with billing off. It grants no repository access, it is used by hand a handful of times, every automated test runs without one, and reissuing it takes about a minute.
**Decision.** The key lives in a file called `.env` at the root of the project, which git ignores, read by seven lines of standard library code that check the environment first and the file second. That order is what lets the scheduled run supply a repository secret later with no code change. `env.example` is the committed template that names the setting and carries no value. The key is never typed into a terminal.
**Consequences.** Nothing new is installed and no fourth dependency is added. Four things were measured or read rather than assumed, and each one moved the answer. MITRE CWE-526 is the only published guidance found that compares these two options directly, and it prefers a protected configuration file to an environment variable, on the grounds of reduced attack surface. Most of the advice usually quoted against files was written about containers in production or about files served over the open web by misconfigured servers, and one widely cited article against them exempts local development in its own text. On this operating system the credential store does not defend against another program running as the same person: a secret written to it was read back in cleartext by a separate process with no prompt, so it protects against a second account and a stolen disk, neither of which is the situation here. And an account-wide variable is stored in cleartext where sandboxed applications can read it, while typing one into this shell writes the value permanently into that shell's history file, because the filter meant to catch sensitive commands does not match a name containing underscores. The task runner option was dropped because it puts the value into the interactive shell, which keeps the file and adds the exposure. Two things could stop being true and would reopen this. A key of this kind can read files uploaded to the provider's own store, which is harmless only because this project uploads none. And it cannot incur a bill only while billing stays switched off on that account.
